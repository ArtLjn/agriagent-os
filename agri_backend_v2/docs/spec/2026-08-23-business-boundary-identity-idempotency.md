# Business 业务边界、身份与幂等规范

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 适用范围 | `agri_backend_v2/business` REST、MCP、Service、ORM、MySQL |
| 关联 Agent | `agri_backend_v2/agent/tools` 中的 Business Skill |
| 目标 | 防止 Skill 重试、自然语言歧义和重复创建导致业务对象错绑或事实重复 |
| 当前状态 | implementation in progress；身份唯一性、引用解析、DDL/ORM/Skill 已落地，事实写入的统一幂等存储仍待后续批次 |

本规范区分“同名”和“同一对象”，也区分“业务上允许两笔相同事实”和“同一条命令被重试”。
Business 不得通过创建接口隐式执行更新，不得通过姓名等展示字段静默选择业务对象。

## 2. Business 边界

Business 是业务数据的唯一写入边界，负责：

1. 校验农场租户边界、对象归属和跨域引用。
2. 定义主数据的自然键、事实记录的幂等键和关联表的唯一性。
3. 对 REST 和 MCP 提供相同的业务规则、错误码和事务语义。
4. 在写入前拒绝歧义，在写入时拒绝冲突，在重试时返回原结果。
5. 保留业务历史；涉及工人、工资、成本和农事记录的删除优先采用停用或软删除。

Agent 负责意图理解、查询候选对象和用户确认；Agent 不负责猜测对象 ID、编排跨表事务或自行去重。

```text
用户表达
  -> Agent 查询候选并消除歧义
  -> Agent 生成确认摘要和 client_request_id
  -> Business 校验身份、唯一性、租户和幂等性
  -> Business 在一个事务中写入并返回结构化结果
```

## 3. 统一写入语义

### 3.1 三类键

| 类型 | 作用 | 示例 |
| --- | --- | --- |
| 自然键 | 判断两个主数据对象是否是同一对象 | `farm_id + worker.phone` |
| 业务主键 | 精确定位对象，更新、删除和关联只能使用它 | `worker_id`、`cycle_id` |
| 幂等键 | 判断同一条写命令是否被重试 | `farm_id + client_request_id` |

自然键冲突和幂等重放不是同一种情况：自然键冲突返回业务冲突；幂等键参数相同则返回首次结果，参数不同则返回 `idempotency_conflict`。

### 3.2 命令规则

| 命令 | 规则 |
| --- | --- |
| `create` | 只创建新对象；不允许命中旧对象后静默更新或直接伪装成功 |
| `get_or_create` | 只允许用于明确声明的基础设施初始化，例如用户设置、默认分类；不得作为通用 Skill 创建语义 |
| `update` | 必须传业务主键；部分更新只能改变明确传入的字段 |
| `delete` | 由领域决定软删除、停用或物理删除；不得破坏历史事实引用 |
| `query` | 姓名、名称、交易方只能用于筛选；返回多个候选时必须保留候选 ID |

所有冲突和歧义错误必须包含 `code`、面向用户的 `message` 和机器可用的上下文，例如 `existing_id`、`candidate_ids`、`field`。

## 4. 主数据边界

### 4.1 工人档案

工人是“农场内的人员档案”，不是由姓名代表的字符串。

| 规则 | 定义 |
| --- | --- |
| 同名 | 允许；姓名不是唯一键 |
| 电话 | 同一农场内，填写后必须唯一；存储前统一规范化空白、格式和空字符串 |
| 电话是否必填 | 数据库可暂时保留可空，以兼容历史数据；农场内已有同名工人时，新建必须提供电话 |
| 同电话创建 | 返回 `duplicate_worker_phone`，携带已有 `worker_id`；不得更新旧档案 |
| 同名无电话创建 | 若已有同名候选，返回 `worker_identity_ambiguous`；要求补充电话或选择已有工人 |
| 更新 | 只接受 `worker_id`；修改电话时再次执行唯一性校验 |
| 停用 | 设置 `inactive`，保留工资和农事历史；电话不释放给另一档案 |
| 重新使用 | 恢复原档案，不能通过再次 `create` 生成第二份人员档案 |
| 外部引用 | 工资、作业单、农事日志必须保存 `worker_id`；`worker_name` 只能作为查询输入或展示快照 |

姓名展示建议使用“姓名 + 电话后四位 + 状态 + worker_id”。当姓名查询结果超过一条时，Business 必须返回候选列表，不得按最早 ID、最近 ID 或数据库返回顺序自动选择。

### 4.2 其他主数据

| 对象 | 身份和重复规则 |
| --- | --- |
| 用户 | `phone` 全局唯一；重复注册返回冲突 |
| 用户设置 | 每个用户最多一条；允许按 `user_id` 创建或更新 |
| 农场 | `uid` 唯一；名称可以重复；当前用户与默认农场关系保持一对一 |
| 作物模板 | 名称不是全局唯一；同农场内完全相同的名称、品种和阶段内容可返回已有模板，但不得覆盖旧模板 |
| 生长阶段 | 同一模板内 `order_index` 唯一 |
| 种植茬口 | 名称是标签，不是身份；同名茬口允许存在，必须使用 `cycle_id` 区分 |
| 种植单元 | 同一茬口内规范化名称唯一；不同茬口可复用“东棚”等物理名称 |
| 成本分类 | 同一农场、同一收支类型、同一规范化名称唯一 |

## 5. 事实记录边界

日志、作业单、工资、成本和赊账属于事实记录。相同日期、金额、分类或备注不代表同一事实，因此不能用内容相似度直接覆盖或拒绝真实业务。

| 事实 | 重复策略 |
| --- | --- |
| 农事日志 | 默认追加；同一命令重试靠 `client_request_id` 防重；参与工人关联使用 `worker_id` |
| 作业单 | 默认追加；同日同类作业可以是多笔；创建和修改必须区分 `work_order_id` |
| 用工明细 | 必须绑定明确 `worker_id`；同一命令使用幂等键；是否允许同一工人在同一作业单多条明细由工资模型另行确定，不能通过姓名猜测 |
| 成本/收入 | 手工记录默认追加；来源于作业单或工资记录时，同一来源只能有一条活动成本记录 |
| 赊账 | 每次赊账独立成账；交易方只是筛选条件；结算必须锁定具体账单，不得按名称覆盖全部账单 |
| 种植计划 | 模板、茬口和种植单元作为一个事务提交；`farm_id + client_request_id` 已是幂等边界 |

## 6. Skill 调用规则

Skill 必须遵守以下顺序：

1. 创建工人前先查询同名和同电话候选。
2. 查询只有一个候选时，将其 `worker_id` 带入后续写操作。
3. 查询有多个候选时，向用户展示姓名、电话后四位、状态并要求选择。
4. 无法唯一识别时不得自动创建工人档案，不得使用姓名的第一条结果。
5. 所有写操作在确认摘要中说明目标对象、影响范围和 `client_request_id`。
6. 同一轮重试必须复用原 `client_request_id`，不得生成新的 ID 绕过幂等校验。

因此以下描述必须删除或改写：

- “同名工人已存在则直接返回（幂等）”。这会把姓名误当作人员身份。
- “通过 `worker_name` 自动建档”。日志和用工只能引用已确认的工人。
- “只要传入姓名即可添加工时”。必须先解析为 `worker_id`。

## 7. DDL、ORM、迁移和工具同步要求

### 7.1 `farm_manager.sql` 是否需要更新

需要，但不能只修改快照文件。目标约束为：

```sql
UNIQUE KEY uq_workers_farm_phone (farm_id, phone)
UNIQUE KEY uq_planting_units_farm_cycle_name (farm_id, cycle_id, name)
```

`phone` 继续允许 `NULL` 时，MySQL 允许多个未知电话；非空电话在同一农场内唯一。规范化电话应由 Service 在写入边界完成，DDL 负责最终兜底。

修改必须同时覆盖：

1. `business/models.py` 的 `__table_args__`；
2. 正向和回滚 migration；
3. `farm_manager.sql` 全量快照；
4. 迁移前重复数据审计。发现重复时必须中止迁移，禁止自动合并或覆盖。

### 7.2 `agent/tools` 是否需要更新

需要。已同步 `manage-workers`、`manage-work-orders` 和 `manage-farm-logs`：写入引用优先使用 `worker_id`，姓名只保留唯一匹配兼容入口，`manage-workers` 不再声明“同名幂等”。

工具描述和参数需要同步：

- `manage-workers`：创建说明改为“同名允许，电话冲突拒绝”；更新必须 `worker_id`。
- `manage-work-orders`：`add_labor` 增加 `worker_id`，`worker_name` 仅作为查询/兼容输入，不能在多个候选中自动选择。
- `manage-farm-logs`：增加 `worker_ids`；`worker_names` 只允许唯一匹配已有档案，不能自动建档。
- 所有事实型写操作增加或透传 `client_request_id`（统一幂等作为后续批次，当前工资写入已支持）。
- Skill 的 `required` 只声明真正执行所需的业务信息，不让模型自行猜 ID。

工具描述不能先于运行时实现宣称新行为。Skill、MCP 参数、Service、ORM 和 migration 应在同一个实现变更中提交。

## 8. 实施顺序与验收

### 第一阶段：工人身份

- 增加电话规范化和农场内唯一校验。
- 删除按姓名静默复用和自动建档路径。
- REST/MCP 对同名、多电话、跨农场访问分别测试。

### 第二阶段：引用和 Skill（本批次）

- 日志、用工、作业单支持 `worker_id`。
- 多候选返回结构化歧义错误。
- 更新所有相关 `skill.md` 和 Skill 元数据测试。

本批次同时完成工人电话和种植单元名称的 ORM、快照 DDL 与正反向迁移约束。

### 第三阶段：统一幂等和剩余自然键

- 为事实型写入建立统一幂等存储或补齐各表幂等字段。
- 增加种植单元、成本分类等自然键约束。
- migration 前执行重复数据报告；发现冲突时停止发布。

### 必须通过的验收

1. 同名不同电话的工人可以同时存在，且工资、日志分别关联正确的 `worker_id`。
2. 同一农场重复电话创建返回业务冲突，不修改原工人。
3. 同名且无电话时不会自动选择或覆盖已有工人。
4. 重试同一写命令只产生一条事实记录。
5. 同一事实使用相同幂等键但修改参数时返回 `idempotency_conflict`。
6. DDL、ORM、migration、REST、MCP 和 Skill 描述对同一规则保持一致。
