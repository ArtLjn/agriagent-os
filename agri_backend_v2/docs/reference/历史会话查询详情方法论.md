# Agent 历史会话查询接口设计方法论

## 1. 背景

传统 Chat 应用：

```
Conversation
    |
    |
 Message
```

历史查询只需要返回：

```json
{
  "role": "user",
  "content": "xxx"
}
```

但是 Agent 会产生：

* 用户消息
* Agent 回复
* 工具调用
* 执行过程
* 过程状态
* 生成结果

因此历史查询接口需要从：

> 查询聊天记录

升级为：

> 查询一次 Agent 会话执行历史

---

# 2. 设计目标

历史查询接口需要支持：

## 2.1 会话恢复

用户重新打开页面：

```
conversation_id
        |
        ↓
加载历史消息
        |
        ↓
恢复 UI 状态
```

---

## 2.2 Agent 过程展示

支持展示：

```
已思考

↓

调用工具

↓

获取结果

↓

最终回答
```

---

## 2.3 分页加载

避免一次返回：

```
1000 条 Agent Event
```

导致：

* 数据量过大
* 首屏慢
* 前端渲染压力

---

## 2.4 增量更新

支持：

* 新消息产生
* 重新生成
* 会话修改

---

# 3. 推荐接口分层

不要设计：

```
GET /conversation/{id}
返回所有东西
```

推荐：

```
Conversation API
        |
        |
        ├── 会话信息
        |
        ├── 历史消息
        |
        └── 执行详情
```

---

# 4. 会话查询接口

## 获取会话基本信息

```
GET /api/v2/conversations/{conversation_id}
```

返回：

```json
{
 "conversation_id":"conv_xxx",

 "title":"农业咨询",

 "created_at":"",

 "updated_at":"",

 "message_count":20,

 "status":"active"
}
```

职责：

只返回：

* 会话元信息
* 状态

不要返回全部消息。

---

# 5. 历史消息查询接口

推荐：

```
GET /api/v2/conversations/{conversation_id}/messages
```

返回：

```json
{
 "items":[

   {
    "message_id":"msg_001",

    "role":"user",

    "content":"帮我查询番茄病害",

    "created_at":""
   },


   {
    "message_id":"msg_002",

    "role":"assistant",

    "content":"番茄常见病害包括...",

    "created_at":""
   }

 ],

 "pagination":{

    "next_cursor":"xxx",

    "has_more":true

 }
}
```

---

# 6. 为什么需要 cursor 分页

不要：

```
?page=1&page_size=20
```

Agent 场景推荐：

```
?cursor=xxx
&limit=20
```

原因：

消息不断新增：

```
page 1

message 1-20


新增10条


page 2

位置变化
```

cursor 更稳定。

---

# 7. Message 字段设计

推荐：

```json
{
 "message_id":"",

 "turn_id":"",

 "role":"user|assistant",

 "content":"",

 "message_kind":"",

 "created_at":"",

 "meta":{}
}
```

核心字段：

| 字段           | 作用          |
| ------------ | ----------- |
| message_id   | 消息唯一ID      |
| turn_id      | 关联一次Agent执行 |
| role         | 用户/助手       |
| content      | 展示内容        |
| message_kind | 消息类型        |
| meta         | 扩展字段        |

---

# 8. message_kind 设计

不要只设计：

```
prompt
final_answer
```

建议：

```
user_input

assistant_answer

thinking_summary

tool_summary

artifact

error
```

例如：

```json
{
 "message_kind":"tool_summary",

 "meta":{
    "tool_name":"web_search",
    "status":"completed"
 }
}
```

---

# 9. 执行详情接口

历史聊天和 Agent Trace 分开。

接口：

```
GET /api/v2/conversations/{conversation_id}/turns/{turn_id}
```

返回：

```json
{
 "turn_id":"turn_001",

 "steps":[

 {
  "type":"thinking",
  "content":"分析用户需求"
 },


 {
  "type":"tool",
  "name":"web_search",
  "status":"completed"
 },


 {
  "type":"answer",
  "content":"最终结果"
 }

 ]

}
```

原因：

普通用户：

只需要：

```
用户
助手回答
```

高级用户：

查看：

```
Agent执行过程
```

---

# 10. 版本控制

建议保留：

```json
{
 "conversation_revision":10,

 "summary_revision":3
}
```

用途：

* 会话更新
* 历史回滚
* Summary 重建
* 多端同步

---

# 11. 推荐最终接口

```
Conversation

GET
/api/v2/conversations/{id}


Message History

GET
/api/v2/conversations/{id}/messages


Agent Trace

GET
/api/v2/conversations/{id}/turns/{turn_id}
```

职责：

```
conversation
    |
    |-- metadata

messages
    |
    |-- 用户可见历史

turn detail
    |
    |-- Agent执行过程
```

---

# 12. 核心原则

一句话：

> **历史会话查询接口负责恢复用户看到的对话状态；Agent 执行详情接口负责恢复 Agent 的运行过程。两者不要混在一个接口。**

你的截图里的接口目前：

```json
conversation
 |
 items
```

其实方向没错。

建议下一步调整：

```
items
 ↓
messages

新增:
turns/detail API
```

这样 SSE 实时流和历史查询可以共用同一套事件模型。
