# farm-manager v2 接口规范

> 日期：2026-08-05
> 范围：agent HTTP + business HTTP REST + business MCP 工具 + SSE 协议

## 0. 架构与边界

```
┌──────────────┐  HTTP/SSE   ┌──────────────┐  MCP/HTTP  ┌──────────────┐
│   前端 Web   │────────────▶│   agent      │───────────▶│  business    │
│  (index.html)│             │  (FastAPI)   │            │  (FastMCP +  │
└──────┬───────┘             │  :8000       │            │   FastAPI)   │
       │                     └──────┬───────┘            │  :9876       │
       │ HTTP REST (查询类)          │ MongoDB            │  /mcp + /api │
       └─────────────────────────────┴────────────────────▶│              │
                                                           └──────┬───────┘
                                                                  │ MySQL
                                                                  ▼
                                                           ┌──────────────┐
                                                           │   business   │
                                                           │   domain DB  │
                                                           └──────────────┘
```

**关键原则：**

- **前端 → agent**：对话/推理类请求走 agent `/chat`（SSE 流式）
- **前端 → business HTTP**：直接查询/管理类请求走 business REST API（如农场状态、农事日志 CRUD、天气查询）
- **agent → business MCP**：ReAct 循环中 LLM 调工具走 MCP 协议
- **business 双协议**：同一端口 9876 同时提供 HTTP REST（`/api/*`）和 MCP（`/mcp`）

| 维度 | agent | business |
|------|-------|----------|
| 协议 | HTTP + SSE | HTTP REST + MCP (Streamable HTTP) |
| 端口 | 8000 | 9876 |
| 调用方 | 前端（对话）、运维（探活） | 前端（直连查询）、agent（MCP 工具） |
| 持久化 | MongoDB (对话历史) | MySQL (业务数据) |
| 框架 | FastAPI | FastMCP + FastAPI (同一进程) |
| 路径前缀 | `/` | `/api/*`（REST）+ `/mcp`（MCP） |

## 1. Agent HTTP 接口（端口 8000）

Base URL: `http://127.0.0.1:8000`

### 1.1 接口总览

| # | 方法 | 路径 | 用途 | 响应类型 |
|---|------|------|------|---------|
| 1 | GET | `/` | Web UI 首页 | `text/html` |
| 2 | GET | `/static/*` | 静态资源（CSS/JS） | `text/css` / `application/js` |
| 3 | GET | `/health` | 健康检查 | JSON |
| 4 | POST | `/chat` | 发送消息（SSE 流式） | `text/event-stream` |
| 5 | POST | `/approve` | HITL 审批（写操作放行） | JSON |
| 6 | POST | `/reset` | 清空对话短期记忆 | JSON |
| 7 | GET | `/turns/{turn_id}` | 查询 turn 状态（轮询兜底） | JSON |
| 8 | GET | `/conversations` | **新增**：对话列表 | JSON |
| 9 | GET | `/conversations/{conversation_id}` | **新增**：对话详情 | JSON |
| 10 | GET | `/traces` | **新增**：Trace 请求列表 | JSON |
| 11 | GET | `/traces/{request_id}` | **新增**：Trace 节点详情 | JSON |
| 12 | GET | `/traces/{request_id}/summary` | **新增**：Trace 聚合摘要 | JSON |

### 1.2 `GET /` — Web UI 首页

返回静态 HTML 页面（`agent/static/index.html`）。

- **请求：** 无参数
- **响应：** `text/html; charset=utf-8`

### 1.3 `GET /static/{path}` — 静态资源

挂在 `/static` 路径下，提供 CSS/JS/图片等静态资源。

- **响应：** 对应 MIME 类型

### 1.4 `GET /health` — 健康检查

用于探活和运维监控。

- **请求：** 无参数
- **响应（200）：**

```json
{
  "status": "ok",
  "pending_approvals": 0
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| status | string | 固定 `"ok"` |
| pending_approvals | int | 等待用户审批的 HITL turn 数 |

### 1.5 `POST /chat` — 对话主接口（SSE 流式）

启动一个 ReAct turn，通过 SSE 流式返回思考/工具调用/最终回答等事件。

**请求体：**

```json
{
  "message": "苏州天气怎么样",
  "conversation_id": "test-sz-001"
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| message | string | 是 | - | 用户消息 |
| conversation_id | string | 否 | `"default"` | 对话 ID，用于关联历史 |

**响应头：**

```
Cache-Control: no-cache
X-Accel-Buffering: no
Content-Type: text/event-stream
```

**响应内容：** SSE 事件流，详见 [§4 SSE 事件协议](#4-sse-事件协议post-chat)

**流程：**

1. 创建 `Turn` 对象（生成 `turn_id`）
2. 将 user message 落 MongoDB（失败降级，不阻塞流程）
3. 初始化 trace 上下文（`conversation_id` + `turn_id`）
4. 运行 ReAct 循环，通过 SSE 流式 yield 事件
5. 流结束后将 assistant 最终回答落 MongoDB
6. 清理 `_active_turns` 和 `_pending_approvals`

**示例：**

```bash
curl -N -X POST http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"苏州天气","conversation_id":"test-001"}'
```

### 1.6 `POST /approve` — HITL 审批

当 agent 想执行写操作（`write_confirm` / `write_high` 风险等级）时，通过 SSE 发送 `approval_required` 事件。前端展示审批按钮，用户决策后调本接口。

**请求体：**

```json
{
  "turn_id": "a1b2c3d4e5f6",
  "decision": true,
  "reason": ""
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| turn_id | string | 是 | - | 从 `approval_required` 事件取 |
| decision | bool | 是 | - | `true`=批准, `false`=拒绝 |
| reason | string | 否 | `""` | 拒绝理由（拒绝时建议填写） |

**响应（200）：**

```json
{
  "ok": true,
  "turn_id": "a1b2c3d4e5f6",
  "decision": true
}
```

**错误码：**

| HTTP | 说明 |
|------|------|
| 404 | `turn_id` 找不到对应 pending approval |
| 409 | 该 `turn_id` 已被审批过 |

### 1.7 `POST /reset` — 重置对话短期记忆

清空 agent 内存中指定 conversation 的短期记忆（不影响 MongoDB 历史记录）。

**请求体：**

```json
{
  "conversation_id": "test-001"
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| conversation_id | string | 否 | `"default"` | 要重置的对话 ID |

**响应（200）：**

```json
{
  "ok": true,
  "conversation_id": "test-001"
}
```

### 1.8 `GET /turns/{turn_id}` — Turn 状态查询

轮询某个 turn 的当前状态。SSE 断线兜底方案，正常流程不需要调。

**Path 参数：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| turn_id | string | 是 | turn ID（从 `meta` 事件获取） |

**响应（200）：**

```json
{
  "turn_id": "a1b2c3d4e5f6",
  "conversation_id": "test-001",
  "status": "running",
  "step_count": 2,
  "pending_approval": null,
  "final_answer": null,
  "error": null,
  "events_count": 5
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| status | string | `running` / `awaiting_approval` / `completed` / `rejected` / `failed` |
| step_count | int | ReAct 循环已执行步数 |
| pending_approval | object\|null | 待审批的工具调用详情（同 `approval_required` 事件 data） |
| final_answer | string\|null | 最终回答（status=completed 时有值） |
| error | string\|null | 错误信息 |
| events_count | int | 已产生的事件总数 |

**错误码：**

| HTTP | 说明 |
|------|------|
| 404 | turn 不存在或已结束被清理 |

### 1.9 `GET /conversations` — 对话列表（新增）

获取最近的对话列表，按最后消息时间倒序。

**Query 参数：**

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| limit | int | 否 | 20 | 返回条数上限（1-100） |
| cursor | string | 否 | - | 分页游标（上一页最后一条的 `conversation_id`） |

**响应（200）：**

```json
{
  "items": [
    {
      "conversation_id": "test-sz-qweather",
      "last_message": "苏州未来3天天气预报如下...",
      "last_role": "assistant",
      "last_at": "2026-08-06 14:08:30.123456",
      "message_count": 4
    },
    {
      "conversation_id": "test-yuhang5",
      "last_message": "明天余杭天气...",
      "last_role": "user",
      "last_at": "2026-08-06 11:22:33.000000",
      "message_count": 2
    }
  ],
  "next_cursor": null,
  "has_more": false
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| items[].conversation_id | string | 对话 ID，用作详情接口的 path 参数 |
| items[].last_message | string | 最后一条消息内容（截断 200 字符） |
| items[].last_role | string | 最后消息角色：`user` / `assistant` |
| items[].last_at | string | 最后消息时间（`YYYY-MM-DD HH:MM:SS.ffffff`） |
| items[].message_count | int | 该对话总消息数 |
| next_cursor | string\|null | 下一页游标，无更多数据为 `null` |
| has_more | bool | 是否还有更多数据 |

**实现要点：** MongoDB 聚合管道 `aggregate` 按 `conversationId` 分组，取每组最后一条消息。

**错误码：**

| HTTP | code | 说明 |
|------|------|------|
| 400 | `invalid_limit` | limit 不在 1-100 范围 |
| 500 | `internal` | 查询失败（MongoDB 不可用时降级返回空数组） |

### 3.5 `manage_farm_logs(operation, ...)`

农事日志统一管理接口，三种操作：

| operation | 风险 | 必填参数 | 说明 |
|-----------|------|---------|------|
| `query` | read | 无 | 查询最近 N 天记录，可按 `cycle_id` 过滤 |
| `create` | write_confirm | `cycle_id`, `operation_type` | 创建农事记录（HITL 闸门） |
| `delete` | write_high | `log_id` | 删除记录（HITL 闸门 + 二次确认） |

- **参数：**
  - `operation`：`query` / `create` / `delete`
  - `cycle_id`：茬口 ID（create 必填，query 可选过滤）
  - `operation_type`：操作类型如「浇水」「施肥」（create 必填）
  - `operation_date`：`YYYY-MM-DD`（create 默认今天）
  - `note`：备注（create）
  - `worker_names`：工人姓名列表（create）
  - `log_id`：记录 ID（delete 必填）
  - `days`：回溯天数（query，默认 7）
  - `limit`：返回上限（query，默认 20）

- **返回示例（query）：**

```json
{
  "count": 2,
  "logs": [
    {
      "id": 28,
      "cycle_id": 3,
      "operation_type": "浇水",
      "operation_date": "2026-08-05",
      "operation_time": "2026-08-05T06:30:00",
      "note": "清晨滴灌",
      "worker_names": ["张三"],
      "created_at": "2026-08-05T06:35:12"
    }
  ],
  "filter": {"cycle_id": null, "days": 7, "limit": 20}
}
```

- **返回示例（create）：** 单条 log dict（同 query.logs[]）
- **返回示例（delete）：**

```json
{"deleted": 28}
```

- **错误码：**

| error code | 触发条件 |
|-----------|---------|
| `missing_cycle_id` | create 未传 cycle_id |
| `missing_operation_type` | create 未传 operation_type |
| `missing_log_id` | delete 未传 log_id |
| `not_found` | delete 的 log_id 不存在 |
| `invalid_operation` | operation 不是 query/create/delete |

## 4. SSE 事件协议（`POST /chat`）

`/chat` 返回 `text/event-stream`，每个事件格式：

```
event: <type>
data: <json>

```

（两个换行结束一个事件）

### 4.1 事件类型总览

| # | 事件类型 | 时机 | data 字段 |
|---|---------|------|----------|
| 1 | `meta` | turn 开始 | `turn_id`, `conversation_id`, `user_input` |
| 2 | `thought` | LLM 思考过程 | `content` |
| 3 | `plan` | LLM 给出多步计划 | `steps[]` |
| 4 | `action` | 工具调用开始 | `tool_name`, `arguments`, `rationale` |
| 5 | `observation` | 工具返回 | `tool_name`, `result`, `error` |
| 6 | `approval_required` | HITL 闸门触发 | `turn_id`, `tool_name`, `arguments`, `rationale`, `risk_level` |
| 7 | `approval_result` | 用户审批完成 | `decision`, `reason` |
| 8 | `final_answer_start` | 最终回答开始流式 | `{}` |
| 9 | `final_answer_delta` | 最终回答增量 | `delta` |
| 10 | `final_answer` | 最终回答完成 | `text` |
| 11 | `error` | 流程错误 | `code`, `message` |
| 12 | `done` | turn 结束 | `status`, `turn_id` |

### 4.2 事件详情

#### `meta` — Turn 元信息

turn 开始时第一个事件，前端用它拿到 `turn_id` 以备后续 `/approve` 或 `/turns/{turn_id}` 查询。

```json
{
  "turn_id": "a1b2c3d4e5f6",
  "conversation_id": "test-001",
  "user_input": "苏州天气怎么样"
}
```

#### `thought` — LLM 思考

LLM 的推理过程（assistant message content）。前端可折叠展示。

```json
{"content": "用户问苏州天气，我需要调用 get_weather 工具..."}
```

#### `plan` — 多步计划

LLM 给出计划步骤时发送（可选，不一定每次都有）。

```json
{"steps": ["1. 调用 get_weather 查询苏州天气", "2. 汇总回答用户"]}
```

#### `action` — 工具调用

LLM 决定调用工具时发送。前端展示为工具卡片。

```json
{
  "tool_name": "get_weather",
  "arguments": {"location": "苏州", "days": 3},
  "rationale": "用户问苏州天气，需要调用天气查询工具"
}
```

> **兜底机制：** 当 LLM 未传必填参数时（如 qwen3.6-flash 偶发问题），agent skill 层会用 `turn.user_input` 兜底替换 params，并通过 `_patch_action_args` 回写 action 事件的 `arguments` 字段，让前端展示真实传给 business 的参数。

#### `observation` — 工具返回

工具执行完成后发送。前端在 action 卡片内补全结果。

```json
{
  "tool_name": "get_weather",
  "result": {"location": "江苏省苏州市", "provider": "qweather", "daily": [...]},
  "error": null
}
```

`error` 非 null 时表示工具执行失败，`result` 为错误详情 dict。

#### `approval_required` — HITL 闸门

写操作（`write_confirm` / `write_high`）执行前触发，前端展示审批按钮。

```json
{
  "turn_id": "a1b2c3d4e5f6",
  "tool_name": "manage_farm_logs",
  "arguments": {"operation": "create", "cycle_id": 3, "operation_type": "浇水"},
  "rationale": "需要创建一条浇水农事记录",
  "risk_level": "write_confirm"
}
```

| 字段 | 说明 |
|------|------|
| risk_level | `write_confirm`（创建类，单次审批）/ `write_high`（删除/涉及钱，二次确认） |

前端收到此事件后：

1. 暂停渲染后续事件（turn 阻塞在 `awaiting_approval`）
2. 展示审批 UI（同意 / 拒绝 + 理由输入框）
3. 用户决策后 POST `/approve`

#### `approval_result` — 审批结果

用户审批后立即发送，告知前端决策。

```json
{"decision": "approved", "reason": ""}
```

`decision` 取值：`approved` / `rejected`。

#### `final_answer_start` — 最终回答开始

LLM 开始流式输出最终回答时发送（空 data）。前端打开流式渲染容器。

```json
{}
```

#### `final_answer_delta` — 最终回答增量

流式 token，前端追加到回答容器。

```json
{"delta": "苏州未来3天"}
```

#### `final_answer` — 最终回答完成

流式结束，前端关闭渲染容器。

```json
{"text": "苏州未来3天天气预报如下：..."}
```

#### `error` — 流程错误

ReAct 循环异常时发送（如 stream crash、LLM 调用失败）。

```json
{"code": "stream_crash", "message": "Connection reset by peer"}
```

常见 code：

- `stream_crash` — SSE 流异常中断
- `llm_error` — LLM 调用失败
- `internal` — 其他内部错误

#### `done` — Turn 结束

最后一个事件，告知前端 turn 已结束。

```json
{"status": "completed", "turn_id": "a1b2c3d4e5f6"}
```

| status | 说明 |
|--------|------|
| `completed` | 正常完成（已有 `final_answer`） |
| `rejected` | 用户拒绝 HITL 审批 |
| `failed` | 流程失败（前面会有 `error` 事件） |

### 4.3 前端处理建议

| 事件 | 处理 |
|------|------|
| `meta` | 保存 `turn_id`，初始化对话气泡 |
| `thought` | 显示思考气泡（可折叠） |
| `plan` | 显示计划步骤列表（可折叠） |
| `action` | 显示工具调用卡片（参数 + 理由） |
| `observation` | 在 action 卡片内补全结果 |
| `approval_required` | 弹出审批按钮，暂停后续渲染 |
| `approval_result` | 关闭审批 UI，恢复渲染 |
| `final_answer_start` | 打开流式渲染容器 |
| `final_answer_delta` | 追加 token 到容器 |
| `final_answer` | 关闭流式渲染容器 |
| `error` | 显示错误提示 |
| `done` | 结束 SSE 连接，清理状态 |

## 6. 认证与安全

当前 MVP 阶段**无认证**，所有接口对外开放。生产环境需补充：

- agent HTTP 接口加 JWT / Session 认证
- business HTTP REST 接口加 token 校验
- business MCP 接口加 token 校验（仅允许 agent 调用）
- `conversation_id` 应与用户身份绑定，避免越权访问他人对话
- business 写操作（POST/DELETE）需 CSRF 防护

## 7. 错误处理约定

### 7.1 HTTP 错误响应格式（agent + business REST）

所有 HTTP 接口错误返回统一格式：

```json
{
  "detail": "错误描述",
  "code": "error_code"
}
```

FastAPI 默认用 `detail` 字段，`code` 为扩展字段。

### 7.2 MCP 工具错误返回格式

business MCP 工具不在 HTTP 层报错，而是在返回 dict 中嵌入 `error` 字段：

```json
{
  "error": "unknown_location",
  "message": "无法解析「xxx」的坐标...",
  "hint": "call search_cities first"
}
```

agent skill 收到含 `error` 字段的返回后，由 LLM 决定下一步（通常是根据 `hint` 调用 `search_cities`）。
